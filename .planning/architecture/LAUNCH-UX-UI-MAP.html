↻ Three-document sync protocol #sync

How these three docs relate

The platform is described from three lenses, each in its own file. Same underlying facts — different views. When something changes, you update the doc for the affected lens; pills + cross-links keep the others honest.

DocLensUpdate it when…
MAP.html System / backend / integrations An integration changes (Clerk, WC, Stream, Sentry, Resend), a webhook is added, a cache layer is built, secrets configuration shifts, infra topology changes
AARON-FRONTEND-ERD.html Routes ↔ libs ↔ tables (data flow) A route is added or removed, a new server lib is added, a migration is renumbered, a D1 table is added or schema-changed
LAUNCH-UX-UI-MAP.html (this doc) Member experience, screen design, decisions A screen's layout/copy/status changes, a new screen ships, a UX decision is made, a persona's access changes

Shared vocabulary (all 3 docs use these pills)

  • 🟢 SHIPPED code merged + verified
  • 🟡 PENDING wired in code, waiting on external action
  • 🔴 NOT BUILT launch blocker, work needed
  • ⚪ EXTERNAL third-party / out of repo
  • 🟣 DECISION blocked on a product decision before work starts

Discipline (do these or the docs drift)

  1. After any merged PR, flip the relevant pill in the doc(s) the change touched. Same commit, no follow-up "I'll do it later."
  2. If a change affects two lenses (e.g. new route = data lens + UX lens), update both files.
  3. Add a one-line entry to that doc's changelog at the bottom.
  4. If a decision is pending (🟣 pill), the decision lives in this doc's Decisions section. Don't scatter decision-tracking across files.

Upgrade path: once these stabilize, a single YAML file (.planning/architecture/state.yaml) becomes the source of truth and a tiny generator script rebuilds all three HTMLs. For now: manual discipline.

⚠ Pending decisions #decisions

These block work. Each card names the question, the options, and the recommendation. Once decided, flip the pill on the affected screen(s) and resolve the card.

D-1 · member_profiles schema conflict

Question: Our 0012_member_profiles defines a public-bio table (display_name, bio, photo_url, is_public). Aaron's 0010_member_profiles_tags defines a training-profile table (location, background, training_goal, alumni_flags, show_in_finder). Same table name, different schemas.

Affects: /people (ours, uses public-bio), /account (his, writes training-profile), /find-partners (his, reads training-profile), /profile (his, reads training-profile)

  • Option A (rec): drop our schema, ship his. Convert /people → redirect to /find-partners. ~30 min, low risk.
  • Option B: rename his table to member_training_profiles. Keep both. ~1 hr, medium risk.
  • Option C: merge schemas into one wide table. ~2 hr, cleanest data model.

Status: 🟣 awaiting Max

D-2 · How visible is gamification at launch?

Question: Max said gamification is post-launch. But /account has a "leaderboard opt-in" toggle and awards points on profile completion. And /profile shows a TP dossier.

  • Option A (rec): ship the toggle (writes to a stub table or member preference); hide the points/dossier UI; /leaderboard is placeholder.
  • Option B: strip every gamification UI element. Add back post-launch.

Status: 🟣 awaiting Max

D-3 · Adopt Aaron's app.css wholesale, or merge?

Question: His design tokens conflict with ours in places. Whole-import gives consistency with his polished components (Nav, Sidebar) but may break our existing pages visually until reviewed.

  • Option A (rec): adopt wholesale, do a 30-min visual sweep of every existing route, fix any obvious breakage.
  • Option B: manually merge the design tokens — slower, lower visual-regression risk.

Status: 🟣 awaiting Max

D-4 · Onboarding flow after first login

Question: Where does a freshly-claimed member land after signup? Options affect /welcome, /account, /dashboard.

  • Option A (rec): /welcome → /account?welcome=1 (must fill profile, can skip) → /dashboard
  • Option B: straight to /dashboard, surface a profile-completion banner on dashboard

Status: 🟣 awaiting Max
